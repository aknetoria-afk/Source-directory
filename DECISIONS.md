# Журнал технических решений

Формат: **Решение → Почему → Альтернативы, которые отклонили**.

## 1. Разбить плоскую таблицу на Sources / Phones вместо одной большой

**Решение:** вынести телефоны в отдельную таблицу `Phones` с внешним ключом `utm_term`, остальные атрибуты (включая URL) оставить в `Sources` с `utm_term` как первичным ключом.

**Почему:** в реальных данных обнаружено, что один `utm_term` может иметь несколько телефонов (кол-во значений «1 ко многим»), из-за чего исходная таблица дублировала целиком строку источника ради одного отличающегося поля. Разделение убирает дубли и делает `utm_term` настоящим уникальным ключом.

**Отклонено:** оставить всё в одной таблице и просто скрывать дубли фильтром — не решает проблему целостности данных и ломает любые агрегации по `utm_term`.

## 2. Изначально вынесли и URL в отдельную таблицу Urls — затем отказались от неё

**Решение:** сначала создали таблицу `Urls` (1:N) по аналогии с `Phones`, т.к. в исходных данных на момент анализа тоже встречались повторы `utm_term` с разными URL. Позже, когда пользователь подтвердил, что **в новой версии процесса один `utm_term` = один URL**, вкладку `Urls` удалили, а `url_base`/`url_с_utm` вернули как обычные столбцы в `Sources`.

**Почему:** решение подстроено под реальное соотношение количества значений; когда бизнес-правило изменилось на 1:1, отдельная таблица только добавляла сложность (лишний `JOIN`/`INDEX-MATCH`) без пользы.

**Альтернатива, которую не стали использовать:** оставить таблицу `Urls` "про запас" на случай, если 1:N снова понадобится — отклонено ради простоты; при необходимости вернуть 1:N-таблицу легко воссоздать по тому же паттерну, что и `Phones`.

## 3. Формула `url_с_utm` вычисляется, а не хранится как текст

**Решение:** `url_с_utm` в `Sources` — формула (`INDEX`/конкатенация по столбцам той же строки), а не статичное значение.

**Почему:** это производное значение от `url_base` + `utm_source` + `utm_medium` + `utm_campaign` + `utm_term`. Если хранить как текст, при любом изменении, например, `utm_source` в справочнике пришлось бы вручную поправлять все ссылки — источник рассинхронизации. Формула гарантирует, что значение всегда актуально.

## 4. Экранирование `?` в формуле через `SEARCH("~?", ...)`

**Решение:** для определения символа-разделителя (`?` или `&`) перед параметрами UTM используется `SEARCH("~?", url)` с тильдой.

**Почему:** и в Excel, и в Google Таблицах `?` внутри `SEARCH` по умолчанию — wildcard-символ (соответствует любому одному символу), из-за чего условие всегда срабатывало как «истина». Экранирование тильдой заставляет `SEARCH` искать буквальный знак вопроса.

## 5. Разделитель аргументов формулы определяется по локали таблицы, а не хардкодится

**Решение:** в коде вычисляется `SEP = (локаль начинается с 'en') ? ',' : ';'`, и все формулы строятся с этим разделителем.

**Почему:** таблица использует русскую локаль, где Google Таблицы ожидают `;` вместо `,` между аргументами функций. Формулы, сгенерированные с `,`, выдавали `#ERROR!`. Автоопределение локали избавляет от необходимости менять код при переносе шаблона в таблицу с другой локалью.

## 6. Google Apps Script вместо сервисного аккаунта / прямого вызова Sheets API

**Решение:** вся автоматизация реализована как Apps Script, привязанный к самой таблице (`SpreadsheetApp.getActiveSpreadsheet()`), а не как внешний сервис с ключом сервисного аккаунта.

**Почему:** у среды выполнения инструмента-исполнителя есть ограниченный список разрешённых сетевых доменов, в который `googleapis.com` не входит — то есть вызвать Sheets API напрямую из внешнего кода физически невозможно. Кроме того, ключ сервисного аккаунта — долгоживущий секрет, передавать который через чат/переписку небезопасно. Apps Script выполняется от имени владельца таблицы без передачи секретов наружу.

## 7. Вызов пересборки через `web_fetch` по URL веб-приложения — отклонено

**Решение:** отказались от идеи дёргать `?action=rebuild&token=...` автоматически со стороны внешнего инструмента.

**Почему:** `script.google.com` запрещает автоматический доступ через `robots.txt` — попытка вызова возвращает `ROBOTS_DISALLOWED`. Ограничение действует независимо от корректности токена или длины URL. Путь остаётся рабочим **только** при переходе по ссылке вручную человеком (в браузере) — поэтому на этом и построена веб-форма.

## 8. Веб-форма (HTML + `google.script.run`) вместо Google Формы или внешнего веб-приложения

**Решение:** интерфейс ввода — HTML-страница, отдаваемая тем же Apps Script деплоем (`doGet` → `HtmlService`), взаимодействующая с сервером через `google.script.run`.

**Почему:** не требует дополнительного хостинга и настройки CORS/аутентификации, использует ту же публикацию, что уже была сделана для пересборки таблиц; в отличие от Google Формы, может показывать **зависимые** (каскадные) выпадающие списки и читать данные из таблицы "вживую" при каждом открытии.

**Отклонено:** Google Forms — не поддерживает налету подгружаемые из таблицы каскадные списки без дополнительного Apps Script поверх самой формы (то есть сложность та же, а гибкости меньше); отдельное внешнее веб-приложение — требует стороннего хостинга и отдельного способа аутентифицированной записи в Google Таблицу.

## 9. Каскадные списки реализованы на клиенте (в браузере), а не запросами к серверу на каждый шаг

**Решение:** весь список значений `Обозначения` (Раздел/Источник/Аналитика/...) загружается один раз при открытии формы (`getGeneratorData()`), дальнейшая фильтрация (Раздел → Источник → Площадка) происходит в JavaScript в браузере.

**Почему:** справочник небольшой (десятки значений), держать его в памяти дешевле, чем делать `google.script.run` на каждое изменение выпадающего списка — это ощутимая задержка в интерфейсе Apps Script HTML Service.

## 10. Резерв `utm_term` — отдельная вкладка с формулой статуса, а не поле «занят/свободен» на той же вкладке

**Решение:** статус `Свободен/Использован` в `Резервные_UTM_term` — формула `COUNTIF(Sources!A:A, ...)`, не ручной чекбокс/флаг.

**Почему:** источник истины — сам факт присутствия `utm_term` в `Sources`. Если бы статус проставлялся вручную (или отдельным флагом при выдаче через форму), он мог бы разойтись с реальностью, если запись в `Sources` попала туда любым другим способом (например, кто-то вручную дописал строку в исходный лист с этим `utm_term`, минуя форму).

## 11. Уведомление о нехватке резерва — email на владельца скрипта, порог — в ячейке, а не в коде

**Решение:** `checkReserveAndNotify()` шлёт письмо через `MailApp.sendEmail` на `Session.getEffectiveUser().getEmail()`, порог сравнения хранится в ячейке `E2` вкладки `Резервные_UTM_term`.

**Почему:** самый простой канал уведомления, доступный без дополнительной настройки (не требует Slack-токенов/вебхуков). Порог вынесен в ячейку, чтобы менять его без правки кода.

**Отложено на будущее:** более широкие каналы уведомлений (чат, Slack) — сознательно не реализованы в первой версии по явному запросу «настроим позже».

## 12. Валидация домена URL — белый список, введённый явно, с проверкой на поддомены

**Решение:** `isAllowedDomain()` сверяет хост ссылки с фиксированным списком `ALLOWED_DOMAINS`, разрешая точное совпадение или поддомен (`*.domain.ru`), с отбрасыванием `www.`.

**Почему:** явный список надёжнее эвристик («похоже на наш сайт») и не даёт случайно проставить метки на чужих доменах, для которых аналитика не нужна ("нет необходимости обогащать utm-метками" — прямая формулировка из требований).

## 13. Категория всегда `"без телефона"` при создании через форму

**Решение:** поле «Категория» не показывается пользователю в форме — жёстко прописано значение `"без телефона"`.

**Почему:** явное требование первой версии процесса — телефоны (колл-трекинг) через форму не выдаются, только utm-метки. Поле оставлено в коде как одна строка, чтобы включить выдачу телефонов в будущем было простой правкой, а не переработкой формы.

## 14. `UTM_Campaign` собирается из года и месяца на момент создания, а не по дате начала кампании

**Решение:** `utm_campaign = РА_utm|Проект_utm|название_ГГГГ_ММ`, где `ГГГГ_ММ` — текущие год/месяц сервера на момент отправки формы.

**Почему:** прямое указание пользователя, наблюдение по старым данным показало смешанные форматы (`день_месяц` и `год_месяц`) — новое правило фиксирует единый формат на будущее, не пытаясь привести к общему знаменателю исторические записи.

## 15. Универсальная нормализация URL (протокол опционален, кириллический алиас) + найденный и исправленный баг проверки доменов

**Решение:** введена функция `normalizeUrl()`, которая перед проверкой домена приводит любой введённый адрес к полному виду — добавляет `https://`, если протокол не указан, и заменяет известный кириллический алиас домена (`эхолеса.рф`) на его канонический punycode-адрес (`xn--80ajrlru9c.xn--p1ai`) через словарь `CYRILLIC_DOMAIN_ALIASES`. Правило применяется одинаково ко всем доменам из `ALLOWED_DOMAINS`, а не только к одному конкретному.

**Почему:** пользователи вводят домен в разных форматах (`dius-mfk.ru` без протокола, `эхолеса.рф` вместо технического punycode-имени) — валидация не должна зависеть от формата ввода, только от итогового хоста.

**Попутно найденный и исправленный баг:** первая версия `isAllowedDomain()` сравнивала хост с разрешённым доменом через `host.indexOf('.' + d) === host.length - d.length - 1`. При `indexOf` возвращающем `-1` (подстрока не найдена) и **случайном совпадении длины** хоста и разрешённого домена это арифметическое выражение тоже давало `-1`, из-за чего сравнение ложно проходило как "истина". На практике это означало, что произвольный домен той же длины символов, что и один из разрешённых (например, `random-site.ru` — 14 символов, столько же в `sever-group.ru`), **ошибочно проходил бы проверку** и получал бы UTM-метки, как будто это домен компании.

**Исправление:** заменено на явную проверку суффикса через `String.prototype.slice()` с предварительной проверкой `host.length > suffix.length`, что не подвержено совпадениям длины:
```javascript
function isAllowedDomain(url) {
  var host = extractHost(url);
  if (!host) return false;
  return ALLOWED_DOMAINS.some(function (d) {
    if (host === d) return true;
    var suffix = '.' + d;
    return host.length > suffix.length && host.slice(host.length - suffix.length) === suffix;
  });
}
```

**Проверено на:** легитимных доменах (в т.ч. с `www.` и поддоменами) и на потенциально вредоносных похожих адресах (`evilsever-group.ru`, `sever-group.ru.evil.com`, `random-site.ru`) — после исправления все ложные срабатывания устранены, легитимные домены по-прежнему проходят.

## 16. Название кампании — реальная валидация (латиница, без разделителей), а не только обрезка пробела

**Решение:** значение поля «Кампания» проверяется регулярным выражением `/^[A-Za-z0-9]+$/` — принимаются только латинские буквы и цифры, без пробелов, кириллицы, дефисов и подчёркиваний внутри слова. Проверка дублируется на клиенте (мгновенная обратная связь) и на сервере (авторитетная проверка перед записью в таблицу).

**Почему:** изначальное требование «одно слово без разделителей на английском языке» в первой версии кода проверялось только частично — обрезался конечный пробел, но ничего не мешало ввести кириллицу, внутренние пробелы или символы-разделители, которые сломали бы формат `UTM_Campaign` (`РА_utm|Проект_utm|название_ГГГГ_ММ`) или дали бы кампании с разным написанием одного и того же по смыслу названия (например, `catalog` и `каталог` в разных записях).

**Отклонено:** разрешить дефисы/подчёркивания как «безопасные разделители» — не стали, так как явное требование пользователя — «без разделителей» в принципе, а не «без пробелов, но с другими разделителями».

## Кириллический символ внутри кода `сallexchange`

В реальных данных значение `utm_source` для площадки «01.04 Сallexchange» записано как `leeds_сallexchange` — где буква **«с» на самом деле кириллическая** (опечатка, допущенная при вводе исходных данных задолго до этого проекта), а не латинская `c`. Внешне в большинстве шрифтов эти символы неотличимы.

**Текущее решение:** словарь `analitikaUtmMap` хранит код для этой площадки **как есть в данных** — `'01.04 Сallexchange': 'сallexchange'` (с кириллической «с»), чтобы новые записи через форму совпадали с исторически накопленными данными по этому источнику при будущей аналитике/агрегации.

**Почему это плохо и потребует внимания в будущем:**
- Любой код или человек, вручную печатающий `callexchange` латиницей (например, копируя из внешней документации площадки-партнёра), создаст **визуально идентичный, но технически другой** `utm_source` — аналитика в Calltouch/Битрикс24/рекламных кабинетах будет считать это двумя разными источниками.
- Такие кириллические омографы (с, е, а, о, р, х и др. совпадают по начертанию с латинскими) — частый источник трудноуловимых багов в датах на стыке разных систем.

**Что нужно сделать, когда будет время:**
1. Провести полный аудит исходной таблицы «Справочник источников» на кириллические омографы в технических полях (`utm_source`, `utm_medium`, `UTM_Campaign`, `URL`) — не только в этом одном известном случае.
2. Договориться с командой, admin'ом рекламных кабинетов и Calltouch/Битрикс24: либо остаться на исторически сложившемся кириллическом варианте везде (и явно задокументировать это как принятую договорённость, а не забытую опечатку), либо провести миграцию существующих исторических записей на латиницу одним разом и с этого момента использовать только латиницу.
3. Добавить в `Code.gs` (в `processSubmission`/`normalizeUrl`-подобный слой) автоматическую проверку на смешение кириллицы и латиницы в служебных полях формы, чтобы подобные опечатки не появлялись впредь независимо от решения по п.2.

Резерв`, `Источник=00.00 Резерв`, привязанных к конкретным ЖК, каждая со своим `UTM_term`. Подтверждено — это был временный/тестовый эксперимент; строки удалены, таблица вернулась к прежнему виду (проверено сверкой полного CSV-экспорта до и после — совпадение 1:1).

## 17. Поиск столбца "Телефон" стал устойчив к переименованию заголовка

**Найденный баг:** вкладка `Phones` оказалась полностью пустой, хотя в «Справочник источников» реально было 355 телефонов. Причина — столбец в исходной таблице был переименован с «Телефон» на **«Дополнительно об источнике»** (данные остались на месте, поменялся только заголовок). Функция поиска колонки по имени (`col('Телефон')`) при таком переименовании возвращала `-1`, и код читал `r[-1]` (всегда `undefined`) вместо реальных значений телефона — цикл, который должен был наполнять `Phones`, просто ничего не находил, без единой ошибки.

**Решение:** добавлена функция `colAny(names)`, которая пробует по очереди несколько вариантов названия столбца и берёт первый найденный:
```javascript
telefon: colAny(['Телефон', 'Дополнительно об источнике']),
```

**Почему это важно на будущее:** поиск столбцов по названию заголовка (а не по фиксированному индексу) сделан специально, чтобы не зависеть от порядка колонок — но он **не защищён от переименования самого заголовка**. Если столбец в исходной таблице переименуют ещё раз — код снова тихо перестанет находить данные, без явной ошибки (это особенно опасно, потому что скрипт не упадёт и не пожалуется — просто вкладка окажется пустой). Если такое повторится с другими столбцами — стоит применить тот же паттерн `colAny` профилактически ко всем полям, а не только по факту находки проблемы.

## 18. Модерация новых записей — столбец "Статус" в той же таблице, а не отдельная вкладка

**Решение:** новые записи из формы пишутся сразу в «Справочник источников» (как раньше), но получают столбец `Статус = "На модерации"` по умолчанию. `rebuildRelationalTabs()` строит `Sources`/`Phones`/`Обозначения` только из строк со статусом **не** "На модерации" и **не** "Отклонено" (пустой статус — то есть все исторические строки, заведённые до появления модерации, — тоже считается "боевым"). Модератор вручную меняет статус на «Одобрено. Добавлено в Колтач» после того, как внёс присвоенный `utm_term` в Колтач (и заполнил `Проект в Колтач`).

**Почему не отдельная вкладка «Модерация»** (альтернативный вариант, который тоже рассматривался): одна таблица проще — не нужно переносить строки между вкладками при одобрении (риск задвоить/потерять запись при переносе), вся история контроля версий/правок остаётся в одном месте.

**Важный нюанс, который пришлось решить отдельно — резерв `utm_term` не должен зависеть от статуса модерации.** Если бы `Резервные_UTM_term` проверял занятость term через `COUNTIF(Sources!A:A, ...)`, а `Sources` при этом исключает записи "На модерации" — term, который только что взяли для черновика, снова показался бы "свободным" в резерве, и его мог бы забрать кто-то другой, создав коллизию. Чтобы этого избежать:
- Статус модератора определяет только участие записи в `Sources`/`Phones`/отчётности.
- Занятость `utm_term` в `Резервные_UTM_term` проверяется по **отдельному, ничем не отфильтрованному по Sources** списку — но **с одним исключением: статус "Отклонено" возвращает term в резерв как свободный**, его можно выдать заново. "На модерации" по-прежнему держит term занятым (заявка ещё не решена). Это осознанный выбор — первая версия логики "сжигала" term навсегда при любом статусе кроме "Одобрено. Добавлено в Колтач", но это было изменено по запросу: отклонённые заявки не должны расходовать ограниченный пул номеров впустую.
- Заодно эта проверка переведена с формулы `COUNTIF` на прямое вычисление в скрипте (`setValues`, а не `setFormula`) — это попутно устраняет исходную причину бага из пункта про `#ERROR!`/локаль: больше никакой зависимости от того, `,` или `;` использовать в качестве разделителя аргументов.

**Побочный эффект, о котором стоит знать:** столбец «Статус» создаётся в «Справочник источников» автоматически при первой отправке формы (если его ещё не было) — руками добавлять не нужно. На весь столбец применяется выпадающий список (На модерации / Одобрено. Добавлено в Колтач / Отклонено) для модератора, но проверка `setAllowInvalid(true)` — значение всё равно можно вписать вручную любое, валидация не строгая (чтобы не блокировать редактирование, если модератор допишет что-то нестандартное).

## 19. Критический баг: обращение к листу "Справочник источников" по позиции, а не по имени

**Найденный баг:** весь код (`rebuildRelationalTabs`, `processSubmission`, `searchSourceRowsMulti`, `highlightDifferencesFromOld`) обращался к рабочему листу через `ss.getSheets()[0]` — "первая вкладка слева по счёту". Это работало, пока «Справочник источников» действительно была первой вкладкой. Когда пользователь создал дубликат-архив с названием **«Справочник источников old»** для сравнения версий, эта копия физически оказалась **левее** основной вкладки (позиция 0), и весь код молча начал бы обращаться к архивной копии вместо реальной — без единой ошибки (то, из-за чего `highlightDifferencesFromOld()` сравнивала вкладку саму с собой и не находила расхождений).

**Решение:** добавлена функция `getSourceSheet(ss)`, которая ищет рабочий лист **по имени** «Справочник источников», а не по позиции. Резервный сценарий (если лист переименуют) — берёт первую вкладку, которая не входит в список служебных (`Sources`/`Phones`/`Обозначения`/`Резервные_UTM_term`) и не содержит «old» в названии (регистр не важен). Все 4 места в коде, где раньше было `ss.getSheets()[0]`, переведены на эту функцию.

**⚠️ Важно помнить на будущее — общее правило, не только про эту конкретную вкладку:**
- **Никогда не создавайте/дублируйте вкладки с рабочими данными так, чтобы они оказались левее «Справочник источников»** в списке вкладок — Google Sheets вставляет дубликат сразу после оригинала по умолчанию, но вкладки можно перетащить мышью в любое место, и именно это (предположительно) привело к описанному багу.
- Если нужно сравнить текущую версию с архивной копией (как в этом случае) — создавайте архив с любым отличимым названием (например, тем же `... old`) и **не двигайте вкладки** относительно друг друга без необходимости. Проверить порядок вкладок можно просто взглянув на них в интерфейсе Google Таблиц (порядок слева → справа).
- Если понадобится новая функция, читающая вкладку «Справочник источников» — использовать `getSourceSheet(ss)`, а не `ss.getSheets()[0]`, даже "для быстроты"/one-off кода.
- Вкладка `Справочник источников old` была удалена пользователем после того, как сверка была сделана — `highlightDifferencesFromOld()` при отсутствии этой вкладки просто вежливо возвращает ошибку "вкладка не найдена", это ожидаемое поведение, а не баг.

## 20. Аудит безопасности (внешнее ревью) — исправлены пункты 1–3 из плана приоритизации

Получено внешнее ревью безопасности (Кирилл Бортов), нашедшее реальные уязвимости. После обсуждения приоритетов выяснилось, что доступ к форме уже ограничен доменом Google Workspace (`Who has access: Anyone within [домен]`), что резко снижает критичность части находок (неавторизованная запись, DoS, гонка на резерве, компрометация токена — модель угрозы меняется с «кто угодно в интернете» на «кто-то из своих сотрудников»). Полный список находок и статус см. в переписке; в этом коммите закрыты 3 самых дешёвых и высокоценных пункта:

**1. Обход whitelist'а доменов (`extractHost`).** Регулярка `[^\/]+` не отсекала `?`/`#`, поэтому `https://evil.com?x=.sever-group.ru` давал host, формально оканчивающийся на `.sever-group.ru`, и проходил проверку — хотя реальный домен был `evil.com`. Исправлено: регэксп теперь останавливается на `/`, `?` и `#`; добавлено отсечение `userinfo` (`user@host`) и порта (`:8080`), чтобы корректно определять именно значимый хост в обе стороны атаки (`evil.com@sever-group.ru` → верно берёт `sever-group.ru`; `sever-group.ru@evil.com` → верно берёт `evil.com` и отклоняет).

**2. Formula injection.** Поля `tip`, `razdel`, `istochnik`, `Телефон`, `Проект в Колтач`, `Аналитика`, `ЖК`, `Ответственный за utm-метку`, `Calltouch/пул номеров` писались в ячейки без экранирования — строка вида `=IMPORTXML(...)` выполнялась бы как формула при следующем открытии таблицы и могла слить данные на внешний сервер. Добавлена функция `sanitizeCell()`: если значение начинается на `=`, `+`, `-`, `@` (или управляющий символ перед ними) — добавляется ведущий апостроф, что форсирует текстовый формат ячейки (в UI апостроф не отображается — визуально ничего не меняется, в том числе для телефонов вида `+7...`).

**3. Токен в публичном репозитории.** Пример `SECRET_TOKEN = 'sever2026'` в `INSTRUCTIONS.md` считается скомпрометированным, так как репозиторий публичный. Заменён на нейтральный пример формата с явным предупреждением не использовать это значение, плюс добавлена заметка: никогда не коммитить в репозиторий реальный токен из рабочего `Code.gs` — держать там только плейсхолдер.

**Отложено сознательно (обсуждалось, но не входит в этот патч):**
- Серверная валидация `tip`/`razdel`/`istochnik` против списков `getGeneratorData()` (защита в глубину).
- `LockService` вокруг взятия резерва (гонка при одновременных сабмитах).
- Не гонять `rebuildRelationalTabs()` на каждый сабмит (производительность, не безопасность).
- Constant-time сравнение токена — риск признан непрактичным при текущей модели угрозы (эндпоинт уже за доменной авторизацией Workspace и `robots.txt`).

**Главный шаг, сделанный не кодом:** ограничение деплоя до `Anyone within [домен]` вместо `Anyone with the link` — это снижает критичность найденных проблем сильнее, чем любая из код-правок, и было сделано первым.
