# Журнал технических решений

Формат: **Решение → Почему → Альтернативы, которые отклонили**.

## 1. Разбить плоскую таблицу на Sources / Phones вместо одной большой

**Решение:** вынести телефоны в отдельную таблицу `Phones` с внешним ключом `utm_term`, остальные атрибуты (включая URL) оставить в `Sources` с `utm_term` как первичным ключом.

**Почему:** в реальных данных обнаружено, что один `utm_term` может иметь несколько телефонов (кол-во значений «1 ко многим»), из-за чего исходная таблица дублировала целиком строку источника ради одного отличающегося поля. Разделение убирает дубли и делает `utm_term` настоящим уникальным ключом.

**Отклонено:** оставить всё в одной таблице и просто скрывать дубли фильтром — не решает проблему целостности данных и ломает любые агрегации по `utm_term`.

## 2. Изначально вынесли и URL в отдельную таблицу Urls — затем отказались от неё

**Решение:** сначала создали таблицу `Urls` (1:N) по аналогии с `Phones`, т.к. в исходных данных на момент анализа тоже встречались повторы `utm_term` с разными URL. Позже, когда пользователь подтвердил, что **в новой версии процесса один `utm_term` = один URL**, вкладку `Urls` удалили, а `url_base`/`url_с_utm` вернули как обычные столбцы в `Sources`.

**Почему:** решение подстроено под реальное соотношение количества значений; когда бизнес-правило изменилось на 1:1, отдельная таблица только добавляла сложность (лишний `JOIN`/`INDEX-MATCH`) без пользы.

**Альтернатива, которую не стали использовать:** оставить таблицу `Urls` "про запас" на случай, если 1:N снова понадобится — отклонено ради простоты; при необходимости вернуть 1:N-таблицу легко воссоздать по тому же паттерну, что и `Phones`.

## 3. Формула `url_с_utm` вычисляется, а не хранится как текст

**Решение:** `url_с_utm` в `Sources` — формула (`INDEX`/конкатенация по столбцам той же строки), а не статичное значение.

**Почему:** это производное значение от `url_base` + `utm_source` + `utm_medium` + `utm_campaign` + `utm_term`. Если хранить как текст, при любом изменении, например, `utm_source` в справочнике пришлось бы вручную поправлять все ссылки — источник рассинхронизации. Формула гарантирует, что значение всегда актуально.

## 4. Экранирование `?` в формуле через `SEARCH("~?", ...)`

**Решение:** для определения символа-разделителя (`?` или `&`) перед параметрами UTM используется `SEARCH("~?", url)` с тильдой.

**Почему:** и в Excel, и в Google Таблицах `?` внутри `SEARCH` по умолчанию — wildcard-символ (соответствует любому одному символу), из-за чего условие всегда срабатывало как «истина». Экранирование тильдой заставляет `SEARCH` искать буквальный знак вопроса.

## 5. Разделитель аргументов формулы определяется по локали таблицы, а не хардкодится

**Решение:** в коде вычисляется `SEP = (локаль начинается с 'en') ? ',' : ';'`, и все формулы строятся с этим разделителем.

**Почему:** таблица использует русскую локаль, где Google Таблицы ожидают `;` вместо `,` между аргументами функций. Формулы, сгенерированные с `,`, выдавали `#ERROR!`. Автоопределение локали избавляет от необходимости менять код при переносе шаблона в таблицу с другой локалью.

## 6. Google Apps Script вместо сервисного аккаунта / прямого вызова Sheets API

**Решение:** вся автоматизация реализована как Apps Script, привязанный к самой таблице (`SpreadsheetApp.getActiveSpreadsheet()`), а не как внешний сервис с ключом сервисного аккаунта.

**Почему:** у среды выполнения инструмента-исполнителя есть ограниченный список разрешённых сетевых доменов, в который `googleapis.com` не входит — то есть вызвать Sheets API напрямую из внешнего кода физически невозможно. Кроме того, ключ сервисного аккаунта — долгоживущий секрет, передавать который через чат/переписку небезопасно. Apps Script выполняется от имени владельца таблицы без передачи секретов наружу.

## 7. Вызов пересборки через `web_fetch` по URL веб-приложения — отклонено

**Решение:** отказались от идеи дёргать `?action=rebuild&token=...` автоматически со стороны внешнего инструмента.

**Почему:** `script.google.com` запрещает автоматический доступ через `robots.txt` — попытка вызова возвращает `ROBOTS_DISALLOWED`. Ограничение действует независимо от корректности токена или длины URL. Путь остаётся рабочим **только** при переходе по ссылке вручную человеком (в браузере) — поэтому на этом и построена веб-форма.

## 8. Веб-форма (HTML + `google.script.run`) вместо Google Формы или внешнего веб-приложения

**Решение:** интерфейс ввода — HTML-страница, отдаваемая тем же Apps Script деплоем (`doGet` → `HtmlService`), взаимодействующая с сервером через `google.script.run`.

**Почему:** не требует дополнительного хостинга и настройки CORS/аутентификации, использует ту же публикацию, что уже была сделана для пересборки таблиц; в отличие от Google Формы, может показывать **зависимые** (каскадные) выпадающие списки и читать данные из таблицы "вживую" при каждом открытии.

**Отклонено:** Google Forms — не поддерживает налету подгружаемые из таблицы каскадные списки без дополнительного Apps Script поверх самой формы (то есть сложность та же, а гибкости меньше); отдельное внешнее веб-приложение — требует стороннего хостинга и отдельного способа аутентифицированной записи в Google Таблицу.

## 9. Каскадные списки реализованы на клиенте (в браузере), а не запросами к серверу на каждый шаг

**Решение:** весь список значений `Обозначения` (Раздел/Источник/Аналитика/...) загружается один раз при открытии формы (`getGeneratorData()`), дальнейшая фильтрация (Раздел → Источник → Площадка) происходит в JavaScript в браузере.

**Почему:** справочник небольшой (десятки значений), держать его в памяти дешевле, чем делать `google.script.run` на каждое изменение выпадающего списка — это ощутимая задержка в интерфейсе Apps Script HTML Service.

## 10. Резерв `utm_term` — отдельная вкладка с формулой статуса, а не поле «занят/свободен» на той же вкладке

**Решение:** статус `Свободен/Использован` в `Резервные_UTM_term` — формула `COUNTIF(Sources!A:A, ...)`, не ручной чекбокс/флаг.

**Почему:** источник истины — сам факт присутствия `utm_term` в `Sources`. Если бы статус проставлялся вручную (или отдельным флагом при выдаче через форму), он мог бы разойтись с реальностью, если запись в `Sources` попала туда любым другим способом (например, кто-то вручную дописал строку в исходный лист с этим `utm_term`, минуя форму).

## 11. Уведомление о нехватке резерва — email на владельца скрипта, порог — в ячейке, а не в коде

**Решение:** `checkReserveAndNotify()` шлёт письмо через `MailApp.sendEmail` на `Session.getEffectiveUser().getEmail()`, порог сравнения хранится в ячейке `E2` вкладки `Резервные_UTM_term`.

**Почему:** самый простой канал уведомления, доступный без дополнительной настройки (не требует Slack-токенов/вебхуков). Порог вынесен в ячейку, чтобы менять его без правки кода.

**Отложено на будущее:** более широкие каналы уведомлений (чат, Slack) — сознательно не реализованы в первой версии по явному запросу «настроим позже».

## 12. Валидация домена URL — белый список, введённый явно, с проверкой на поддомены

**Решение:** `isAllowedDomain()` сверяет хост ссылки с фиксированным списком `ALLOWED_DOMAINS`, разрешая точное совпадение или поддомен (`*.domain.ru`), с отбрасыванием `www.`.

**Почему:** явный список надёжнее эвристик («похоже на наш сайт») и не даёit случайно проставить метки на чужих доменах, для которых аналитика не нужна ("нет необходимости обогащать utm-метками" — прямая формулировка из требований).

## 13. Категория всегда `"без телефона"` при создании через форму

**Решение:** поле «Категория» не показывается пользователю в форме — жёстко прописано значение `"без телефона"`.

**Почему:** явное требование первой версии процесса — телефоны (колл-трекинг) через форму не выдаются, только utm-метки. Поле оставлено в коде как одна строка, чтобы включить выдачу телефонов в будущем было простой правкой, а не переработкой формы.

## 14. `UTM_Campaign` собирается из года и месяца на момент создания, а не по дате начала кампании

**Решение:** `utm_campaign = РА_utm|Проект_utm|название_ГГГГ_ММ`, где `ГГГГ_ММ` — текущие год/месяц сервера на момент отправки формы.

**Почему:** прямое указание пользователя, наблюдение по старым данным показало смешанные форматы (`день_месяц` и `год_месяц`) — новое правило фиксирует единый формат на будущее, не пытаясь привести к общему знаменателю исторические записи.
